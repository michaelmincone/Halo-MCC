Request4.mvar: over-quota Forge World variant
Inspected 2026-10-18. Source file and installed game were not changed or run.

RESULT
The description accurately describes the saved object records. This variant
contains 511 independent placements, including 256 Coliseum Walls. It bypasses
the ordinary Forge category quotas and contains inconsistent budget accounting.
It does not increase the 651-slot saved-placement table.

could produce these records. Merely raising a quota maximum in an otherwise
unmodified Forge editor is not established as sufficient to create this file.

WHY THE STOCK ENGINE CAN KEEP THE EXTRA PLACEMENTS
Fresh targeted Ghidra decompilation and Capstone disassembly were performed on
the installed PC haloreach.dll (no target execution):
SHA-256: 738dd2d24ea3aea12e1ee9aa4a61094bf116027d42004c35a19e5048608b0894
All addresses below are preferred VAs for that binary only, not Xbox addresses.

1. New object placement: 0x18006e7bc
   Compares the category's placed byte at +0xd642 + 3*quota_index with the stock
   palette maximum, then requests a free saved slot. Ordinary Forge creation
   therefore applies a category gate that an external authoring path can avoid.

2. Existing-variant copy/rebuild: 0x18006c290
   Initially copies/clamps quota maximums, clears placed counts, then walks the
   fixed 651-record source array and copies eligible occupied placements. The
   placement-copy loop does not stop at a quota's maximum. For every copied
   placement, it increments a one-byte placed count. Afterwards it raises each
   quota maximum to at least its rebuilt byte count. Consequently 100 saved
   lights can survive the initial clamp to the stock light maximum, while 256
   saved walls rebuild as a placed count of zero. This routine also has a
   current-map path that recomputes budget from the byte counts; the saved
   10000 should not be assumed to remain the displayed Forge budget.

3. Variant validation: 0x18006c948, with palette helper 0x18006c848
   Checks version/map/palette compatibility. Its occupied-record loop checks
   category and subitem validity and clears invalid references. That loop does
   not cull otherwise valid placements just because their category exceeds the
   stock maximum. Palette CRC compatibility has its own historical mapping.

4. Existing-slot instantiation: 0x18006ed04
   Resolves the saved slot's stock tag and creates the engine object. This is a
   separate path from the Forge add-object routine's category-cap check.

5. Quota recount/serialization: 0x18006de38 / 0x18006bc20
   The recount accumulator itself is a byte; serialization writes three 8-bit
   quota values. Both corroborate 256 -> 0 bookkeeping behavior. No extension
   of the object array is involved.

XBOX INTERPRETATION
The receiving console needs stock object definitions and an accepted variant
format, both of which these records use. The variant supplies placements, not
new object assets or executable patches. The checked PC paths explain why a
normal engine can load content that its own Forge placement UI would refuse
to create. The user's report that this particular map works on Xbox supplies
the console observation; this investigation did not run or disassemble an
Xbox build. It does not prove 100 lights all illuminate simultaneously, every
possible edit/resave preserves the same counters, or more than 651 independent
saved placements are possible.

CORRECTION TO EARLIER WORKSPACE CONCLUSION
The earlier statement that an 8-bit quota row prevents more than 255 saved
objects in a category was too strong. The counter cannot represent 256, but
the separate object array can contain 256 records referencing that category.
This sample demonstrates the distinction directly. The separate 651-slot
capacity conclusion is unaffected: this map uses 511 slots and leaves 140 free.
